# エンドポイント定義のアプローチ

1. ユースケース整理: それぞれのユースケースを洗い出し、まとめる。
2. API候補洗い出し: それぞれのユースケースについて、HTTPエンドポイントなのか他の実装（ws, wh, push通知,,,）なのか、そもそも内部ロジックやイベントであってAPIではないのか、など。
3. リソース設計: エンドポイントグループ。

ここまでmarkdownやmiroなど、

---

ここからopenapiに。

1. エンドポイント一覧: openapi.yamlに各種エンドポイントパス（と分割ファイル）を記述
2. エンドポイント設計の詳細: それぞれのグループに対して、エンドポイントの詳細をきめる
   1. 全体
      1. エンドポイントパス
      2. タグ
      3. 認証
   2. それぞれ
      1. メソッド
      2. タグ
      3. 要約
      4. 概要
      5. ID
      6. パス・クエリパラ（の定義と参照設定）
3. 認可: だれが叩けるか。
   - 他人の予定は見れないが、課金プラン一覧は誰でも見れる、などを「x-role.role.descriptionの定義とx-required-role.roleによるドキュメント付与」などで表現
   - ただし、複雑なロール不要な場合は「あるエンドポイントだけ`security: []`で非ログインユーザでも利用可能」のようにするだけで十分
4. エラー形式定義（DTO）: エラー時のレスポンス
5. Req/ Res形式定義（DTO）: リクエスト・レスポンスの形式
6. examples: Req/ Resのサンプル
7. components共通化
